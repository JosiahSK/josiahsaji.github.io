ESP32 micro-ROS 2WD
Differential Drive Robot

Bridging the standard ROS 2 navigation stack directly to embedded microcontroller hardware over wireless UDP transports, with 4-pin hardware PWM motor control and deterministic failsafe watchdogs.

micro-ROS (XRCE-DDS) ESP32 DevKit V1 Wi-Fi UDP Transport geometry_msgs/Twist LEDC Hardware PWM Failsafe Watchdog (500ms)
// 01 — overview & objectives

The Problem: Embedded Middleware Fragmentation

Integrating physical microcontrollers with ROS 2 traditionally required complex serial bridges, custom ASCII command parsers, or serial-to-socket converters (e.g. legacy rosserial). These ad-hoc solutions suffer from buffer overflows, lack of standardized message types, fragile reconnection logic, and tethered cables that hinder free mobile robot testing.

Project Objectives: Deploy a native, lightweight micro-ROS client on an ESP32 microcontroller to subscribe directly to standard geometry_msgs/msg/Twist over Wi-Fi (UDP). The firmware transforms linear and angular velocity commands into 8-bit hardware PWM signals across a 4-pin dual H-bridge motor driver, incorporating deadband stiction compensation and safety watchdogs.

1000 Hz PWM Switching Frequency
500 ms Command Timeout Watchdog
8-Bit LEDC PWM Resolution (0–255)
0 ENA/ENB 4-Pin Pure Directional PWM

Verification Status: Benchtop Hardware & UDP Teleop Tested

This implementation has been benchtop-tested on physical ESP32 DevKit V1 hardware wired to an L298N/DRV8833 dual H-bridge motor driver and 2WD chassis. Verified Wi-Fi UDP message transport from a Linux PC running the official Docker micro_ros_agent, with oscilloscope-verified PWM motor signals. Note: Currently open-loop; closed-loop wheel encoder feedback is listed in the roadmap.

Firmware Architecture & Key Implementation Highlights

rclc & micro-ROS
Native micro-ROS Client Over UDP

Integrated the micro_ros_arduino stack using official eProsima Micro XRCE-DDS client primitives. Configured Wi-Fi transport routines connecting directly to the host agent IP over port 8888, eliminating the need for intermediate serial wires or custom serialization protocols.

kinematics mixing
Normalized Differential Drive Kinematics

Implemented differential drive conversion mapping linear velocity ($v$) and angular yaw rate ($\omega$) to wheel speeds ($v_L = v - \omega$, $v_R = v + \omega$). Includes dynamic normalization: if either wheel command exceeds 1.0, both speeds are scaled proportionally to preserve turning radius without motor clipping.

motor dynamics
Nonlinear Stiction Deadzone Compensation

DC motors and gearheads suffer from static friction, failing to rotate below low duty cycles. Designed an active deadband compensation function (MIN_PWM = 60): any velocity command above $\pm0.05$ immediately jumps to the minimum dynamic threshold and scales smoothly up to 255.

safety watchdog
Deterministic Failsafe Cutoff

Mobile robots running over wireless links face network drops and Wi-Fi disconnects. The main execution loop continuously monitors millis() - lastCmdTime: if no valid /cmd_vel packet arrives within 500 ms, the hardware PWM immediately resets to 0 on all pins, preventing runaway robots.

// 04 — firmware implementation

Core Firmware Logic & Code References

The firmware is written in C++ for the Arduino/ESP-IDF framework. Here are the core routines handling velocity reception, mixing, deadband thresholding, and the hardware safety timer:

// Excerpt from: firmware/esp32_microros_2wd/esp32_microros_2wd.ino void cmd_vel_callback(const void * msgin) { const geometry_msgs__msg__Twist * m = (const geometry_msgs__msg__Twist *)msgin; // Normalize inputs against calibrated maximum ratings float lin = constrain(m->linear.x / MAX_LINEAR, -1.0, 1.0); float ang = constrain(m->angular.z / MAX_ANGULAR, -1.0, 1.0); // 2WD Differential Drive Kinematics Mixing float left = lin - ang; float right = lin + ang; // Preserve commanded turning curvature if motor saturation occurs float maxMag = max(fabs(left), fabs(right)); if (maxMag > 1.0) { left /= maxMag; right /= maxMag; } // Map velocity to 8-bit PWM with stiction thresholding int leftPwm = toPwm(left); int rightPwm = toPwm(right); driveMotor(M1A, 0, M1B, 1, leftPwm); driveMotor(M2A, 2, M2B, 3, rightPwm); lastCmdTime = millis(); // Reset watchdog timer } int toPwm(float v) { if (fabs(v) < 0.05) return 0; int pwm = (int)(fabs(v) * (255 - MIN_PWM)) + MIN_PWM; return v > 0 ? pwm : -pwm; }

// 06 — engineering decisions

Design Decisions & Trade-Offs

Wi-Fi UDP vs. USB Serial micro-ROS

Decision: Wireless UDP transport (set_microros_wifi_transports).
Rationale: While serial connections offer negligible packet drop, physical USB cables constrain robotic mobility. Wi-Fi allows free arena navigation and mirrors real-world factory AGV deployment topology.

4-Pin Pure PWM vs. 2-Pin DIR+PWM

Decision: 4-pin pure PWM control (no separate ENA/ENB jumpers).
Rationale: Many compact dual H-bridge modules (DRV8833, L9110S) omit dedicated enable pins. Applying complementary PWM directly to forward and reverse pins provides active regenerative braking on 0V and reduces wiring complexity.

Dynamic Normalization vs. Raw Clamping

Decision: Proportional scaling by maxMag.
Rationale: Simple clamping at $\pm1.0$ causes distortion of commanded turning curvature when forward and angular components add up beyond motor limits. Scaling both wheels maintains the robot's intended geometric path.

Client-Side Watchdog vs. Server Heartbeat

Decision: Local 500 ms deadline timer on ESP32.
Rationale: If Wi-Fi drops completely, a remote heartbeat check cannot reach the robot. A local autonomous watchdog guarantees safety even in total network blackout scenarios.

// 07 — limitations & roadmap

Known Limitations & Future Engineering Steps

Current Limitations

  • Open-loop actuation: lacks optical wheel encoders to measure real ground velocity.
  • No odometry publishing (nav_msgs/msg/Odometry and tf2) back to host Nav2 stack.
  • Wi-Fi connection depends on pre-configured 2.4 GHz credentials in config.h.

Future Improvements

  • Integrate dual-channel optical wheel encoders and publish real-time /odom over micro-ROS.
  • Implement discrete PID closed-loop velocity controller inside ESP32 timer interrupts.
  • Add I2C MPU-6050 IMU publisher for onboard sensor-fused orientation tracking.
