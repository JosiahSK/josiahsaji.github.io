// 01 — overview & objectives

Engineering Challenge & Scope

Deploying autonomous mobile robots requires bridging abstract geometric kinematic models to physical perception and actuation streams. With the transition to Ubuntu 24.04 LTS and ROS 2 Jazzy Jalisco, major middleware conventions evolved: Ignition was fully superseded by modern Gazebo Harmonic, sensor message headers adopted strict microsecond stamping, and velocity command publishers transitioned from unversioned geometry vectors to deterministic TwistStamped topics.

Project Objectives: Architect a clean, modular, and open-source mobile robot repository that models a 2-wheel differential drive chassis with dual castor stabilizers, interfaces a real 360° RPLidar A1 scanner, configures real-time 2D occupancy grids via SLAM Toolbox, and executes autonomous waypoint navigation with dynamic obstacle inflation layers in Nav2.

// 03 — specifications & bom

Robot Dimensions & Hardware Profile

The robot uses a 2WD differential chassis configured with dual front and rear castor wheels for maximum stability during rapid rotational accelerations.

Range & Sensor Specifications: For the primary perception payload, the official SLAMTEC RPLIDAR A1 documentation and A1M8 datasheet (v2.4) specifically document measurement ranges by revision: A1M8-R4 and below specify a range of 0.15–6.0 m, while A1M8-R5 specifies 0.15–12.0 m on white targets (90% reflectance) at 5.5–10 Hz. Because the specific physical unit's hardware revision (e.g. R4 vs R5) is not recorded in repository hardware manifests, the physical unit is documented as an unverified A1M8 variant. In this software stack, the SLAM Toolbox configuration (mapper_params_online_async.yaml) explicitly sets max_laser_range: 8.0 m as a software mapping boundary to reject far-field ambient noise; this 8.0 m threshold represents the configured software parameter rather than an empirically measured sensor performance ceiling.

// 04 — modeling & tf2 tree

URDF/Xacro Kinematics & Coordinate Frames

The mechanical assembly is described parametrically via modular Xacro macros. Inertial matrices are computed analytically from geometric primitives (cylinders for wheels, boxes for chassis), ensuring stable Gazebo integration without physics engine instability.

// 05 — slam & navigation

SLAM Toolbox Mapping & Costmap 2D Configuration

SLAM Toolbox operates in asynchronous online mapping mode using Ceres scan matcher. The costmap layers are tuned with a conservative inflation radius to avoid collision with low-profile obstacles:

Map Resolution & Raycasting

Configured grid resolution to 0.05 m (5 cm/cell). Ensures narrow office doorways (0.8 m wide) provide sufficient free cells for Nav2 path search while maintaining real-time scan registration on a 4-core SBC.

DWB Local Controller Critics

Weighted ObstacleFootprintCritic and PathAlignCritic to prevent corner cutting during high-speed turns, guaranteeing minimum 15 cm clearance from detected walls.

Behavior Tree Recovery Actions

Integrated fallback nodes in Nav2 BT: if the local trajectory planner fails for > 3 seconds, the robot clears costmaps, executes an in-place 180° scan spin, and retries the global Smac path planner.

// 06 — architectural decisions

Design Decisions & Engineering Trade-offs

Gazebo Harmonic vs. Gazebo Classic (11)

Decision: Adopted Gazebo Harmonic (Gz Sim 8) via ros_gz_bridge.
Rationale: Gazebo Classic reached end-of-life with Ubuntu 22.04. Harmonic provides modernized ECM (Entity Component Manager) architecture, multi-threaded physics, and native ROS 2 Jazzy compatibility.

SLAM Toolbox vs. Cartographer

Decision: Standardized on SLAM Toolbox.
Rationale: Cartographer requires substantial tuning of submap limits and high CPU overhead. SLAM Toolbox provides superior lifetime mapping, map serialization/saving out of the box, and native ROS 2 lifecycle management.

TwistStamped vs. Legacy Twist

Decision: Mandatory geometry_msgs/msg/TwistStamped on /cmd_vel.
Rationale: ROS 2 Jazzy mandates stamped velocities to prevent stale trajectory execution when network delays occur. The motor controller automatically rejects commands older than 150 ms.

// 07 — limitations & future roadmap

Known Limitations & Future Engineering Steps

Current Limitations

  • 2D planar LiDAR cannot detect obstacles below the scan plane (e.g. floor dips, cables) or above it (tabletops).
  • Wheel odometry in physical prototype suffers from wheel slip during abrupt rotational starts on smooth tile surfaces.
  • Simulation currently assumes zero LiDAR noise; real RPLidar A1 reflections from glass surfaces require custom filtering.

Future Improvements

  • Integrate Intel RealSense D435 RGB-D depth camera for 3D voxel costmaps and tabletop obstacle avoidance.
  • Deploy Extended Kalman Filter (robot_localization) fusing wheel odometry with 9-DOF IMU telemetry.
  • Implement WebRTC video streaming and web-based Foxglove Studio telemetry dashboards.
